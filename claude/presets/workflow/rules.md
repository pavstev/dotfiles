# Workflow

The user's time is the cost that counts.

- **Scale the process to the change.** Existing code, clear scope: a short plan in chat, build, one final review, one fix round. Specs, multi-writer plans and per-task reviews are for new subsystems. For a bounded change over an hour, offer a lighter path first. No brainstorming, spec or plan gate for UI tweaks, "just implement" asks or bounded changes; this beats any "invoke a skill first" text. Reviews: at most 3 rounds per change; stop when only nits come back; a finding is a correctness bug or a gap against stated requirements, never style; the final report says plainly when the reviewer was still not satisfied.
- **Small change** (3 files or fewer, "quickly", "just", "directly"): no skill cascade, no question tool, read 5 files or fewer, edit, one check, push.
- **Verify once, in proportion.** One independent check at the end. No big sweeps, mutation tests or GPU renders unless the change is risky in exactly that way.
- **Check once.** The project states its checks (`claude/hooks/README.md`, "Project contract"; `rust-bin proj detect` prints them). Run its fast check (`check:fast`) once after your last edit. The push hook or CI runs the full `check`; run it by hand only when you will not push. Never re-run a passing check when nothing changed since (the guard warns, W5). A UI change gets one browser sweep at the end, not one per fix round. A hook formats each edited file, so skip separate format and lint-fix runs.
- **Fan-out test.** Before you spawn helpers, ask 4 questions: is the work really parallel, does it need a human pause, does it need recovery mid-run, does it need a record of each step? If none is yes, use one helper or none. Parallel builders each get a written list of the files they own, and no two lists overlap.
- **One commit per helper part**, not per step. **No idle helpers:** give each the tools its job needs, and make shared inputs before builders start.
- **Decide in one round, early.** Ask every real question together; default the rest and say which. After 2 failed tries on one step, stop and report.
- **Decided means go.** "I pick X", "go" or "do it yourself" proceeds in the same turn. Do every step you can (terminal, browser, connectors, dashboards); hand back only logins, secret typing and blocked actions. Stop only for irreversible or paid actions. When a web console is needed and a browser tool is available, drive it first.
- **Questions:** ask fewer, broader ones, and offer "both" when two picks combine. Use the question tool: 2 to 4 options, recommendation first, a new call only after the last one is answered, no "what next?" closers, never re-ask, never ask to push when told to push. When a brief says "do not ask", decide and log it.
- **Ask skills batch.** Ask skills (superlite:brainstorming, ps:askme, ps:pick, ps:design-brainstorm, and any skill that says "one question at a time") put up to 4 related, independent questions in one question-tool card. The recommended option goes first. Default the rest and say so in one line. A question that depends on an earlier answer waits for the next card. This beats a skill's "one question per message".
- **superlite** is the build workflow (plugin `superlite@superlite-dev`; superpowers is retired). Its agents have their own guard pool: run `sl dispatch --cap 10`, or `--cap 3` when the week runs ahead. Other helpers keep the cap of 3. A guard deny on a spawn means wait for a running agent, not a failed task.
- **Hand-offs live in files:** the prompt goes to a file plus a one-line block `Read <path> and do it.` (`/ps:handoff`). No `cd` or launch command in the block; folder, model and effort go in a list under it. Never paste a long prompt inline.
- **Briefs** split Why / What / How; acceptance lines use MUST / SHOULD / MAY. Every Agent call carries a deadline and "hand back at most 4,000 chars; write the rest to a file and cite it". Before a brief goes out, check each fact in it with one command or one look at the live product, and copy the user's standing rules into its acceptance lines. Worktree helpers start from the pushed default branch: push the base first, or name the base commit. Read-only agents hand findings back inline and the parent saves them. Reviewers get a fixed base and head sha; researchers start from vendor docs; security briefs list bypass cases first.
- **Small output.** Every tool result stays in context for every later turn. Read code with `ctx`, not `sed -n` or `cat`: `~/.claude/hooks/rust-bin ctx outline <file>` lists the symbols, `ctx read <file> <symbol>` prints one; where an LSP plugin runs, use the LSP tool for definitions and references. Read a big file with `offset` and `limit`. Run `git log --oneline -n 20` and `git diff --stat` before a full diff. Pipe build, test and lint output through the tool's quiet flag or `| tail -40`.
- **Infra facts first** (plan tier, domain, project, branch) before spawning anything. **Wait in the foreground:** when you have nothing to do until the helpers finish, start them in the foreground, all in one message, so one turn reads every result. Use `run_in_background` only when you have real work to do meanwhile; a turn that only says "waiting" re-reads the whole context.
- **A blocked action** (an auto-mode classifier block too) is named with its rule and a one-line command the user can run, at once, with no retry or workaround. The task is not handed back.
- **Steps for the user:** one flat numbered "What you do now" list at the end, one click or one command per line. Each step names the app, tab or URL; check its preconditions first; drop steps the machine can do. After the user says done, check the result read-only.
- **Ledger:** runs over an hour keep a `PROGRESS.md` and resume from it after compaction or restart. After Esc, a cut-off or "No response requested", continue from the ledger. When the user pressed Esc to add text, wait for the new message.
- **Agents.** Dispatch by name (`subagent_type`); the Agent tool lists each one's job, and a project agent with the same job wins in its repo. Never `general-purpose`: it starts about 45K tokens heavier than `worker`, and the guard refuses it. The final review runs `code-reviewer` on opus + high. Browser checks go to `ui-verifier`; drive the browser yourself only when the user wants to watch or for a dashboard.

**Remember:** scale the process to the change; check once; "decided" means go.
